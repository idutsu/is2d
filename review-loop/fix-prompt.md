# is2d：利用者の返事のとおりに直す（Claude）

is2d（Rust・eframe/egui の2Dアニメ制作ソフト。目標は「軽量・高速・安全」）のゼロベースレビューの結果を、利用者に手紙で知らせ、利用者が返事を書きました。あなた（Claude）は、その返事のとおりに直してください。直したものは、このあと別の AI（Gemini）が1件ずつ審査し、落とされたものは取り消されます。

## 1. 依頼文で渡されるもの

- `<作業場所>`：直す所（リポジトリのフォルダ。HEAD は対象コミット `<C>`）。ここだけを書き換える
- `<C>`：対象コミット（40桁）
- `<まとめ>`：2つの AI の報告書をまとめた `summary.md`（課題の ID は M-001 から）
- `<手紙>`：利用者に送った手紙（直す順番の案・決めてほしいこと）
- `<返事>`：利用者の返事
- `<結果>`：あなたが書く結果のファイルのパス

## 2. 直すもの

- 返事で直すように言われたものだけを直す。「おすすめのとおり」は、手紙の「この順に直すのがよいと思うもの」の全部と、「決めてほしいこと」のおすすめを選んだこととする
- 「決めてほしいこと」は、返事の答えのとおりにする。答えが無い「決めてほしいこと」にかかわる課題は直さない
- 返事の意味が分からない所は、推測で直さない。結果に「返事が分からなかった」と書く
- 返事に、前に直したものを戻すように書いてあれば（例：「M-003 の直しを戻して」）、そのコミットを `git revert` で戻す。どのコミットかは、前の巡の報告とコミットメッセージ（課題の ID が書いてある）で探す
- 手紙の順に、1件ずつ（同じ根本原因の組は1組ずつ）直す

## 3. 1件ずつの進め方

1. **確かめる**：まとめの課題を、作業場所のコードで確かめる（行番号はずれていることがある）。問題が無ければ直さず、結果に「確かめたら問題が無かった」と理由と一緒に書く
2. **同じ目的の仕組みを探す**：新しい関数・判定・数値を書く前に、同じ目的のものが無いか grep で探す。あれば、それを使うか、1つにまとめる
3. **原因に効く直し方で直す**
   - 症状を潰す直しはしない：決め打ちの数値を変える・足す、特定の場面だけの分岐、失敗したらやり直す処理、別の仕組みへの逃げ道
   - 原因に効く直し方のうち、一番単純なものにする。仕組み（関数・状態・分岐・キャッシュ）が減る直し方を優先する
   - 同じ目的の2つ目の仕組みを作らない。写しを手でそろえる仕組みを作らない
   - 作品の量（図形数・フレーム数・ファイルの大きさ）に上限を足さない。作品のデータを削る仕組み、保存を拒む仕組みを作らない
   - 古い版のファイルを開くための仕組みは作らない（リリース前なので、古い版のファイルは開かない決まり）
   - 時間の目標は、Apple M1 での見込み（測った時間 × チップの倍率：M1 ×1、M2 ×1.2、M3 ×1.4、M4 ×1.7、M5 ×2）で、編集操作 50ms、再生・ドラッグ中の1コマ 41.6ms
4. **テストを足す**：その課題が直ったことを確かめるテストを `src/tests.rs` に足す。直す前のコードで失敗し、直した後で通ること
   - 直した所（`src/tests.rs` 以外）だけを一時的に直す前に戻し（例：`git stash push -- <テスト以外の直したファイル>`）、そのテストを流して失敗することを確かめる。確かめたら直した所を戻す（`git stash pop`）
   - 新しい関数を使うために前のコードでコンパイルできないときは、そう書く
5. **速さ・メモリの課題**は、直す前と後を測る。計測のための一時的なコードはコミットしない
6. **説明書き**：利用者から見た挙動が変わるなら DOCUMENT.md、作りが変わるなら ARCHITECTURE.md・GEOMETRY.md を直す
7. **確かめる**：`cargo fmt`、`cargo test --release`（全部）、`cargo clippy --release --all-targets -- -D warnings`（警告 0）が通ること。通らなければ直すか、その件をやめて元に戻す（`git checkout .`）
8. **コミットする**（1件か1組で1コミット。プッシュはしない）。メッセージは次のとおり
   - 1行目：何をしたか（日本語で短く）
   - 本文：課題の ID（M-xxx と元の ID）、起きていたこと、原因、直し方、同じ目的の仕組みを探した結果（grep した言葉と、見つけたもの）、足したテストと「直す前のコードで失敗することを確かめた」、計測した数字（あれば）、全テストの数と clippy の警告数

## 4. 直さずにやめるもの

- 直すのに設計からの作り直しが要るもの（本番のコード（`src/tests.rs` 以外）の変更が、`cargo fmt` で整形した後でおよそ 300 行を超える、または作りの柱（文書・地図・キャッシュ・Undo の持ち方）を変える）。結果に「設計が要る」と書き、直し方の筋を3行以内で添える
- 原因に効く直し方が見つからないもの。見つからなかった理由を書く
- 直すと、ほかのテストが壊れ、壊れない直し方が見つからないもの

## 5. 結果（`<結果>`）

1行に1件、次の形で書く。

```
M-001 <コミットの7桁> <利用者から見て何が変わるかを一言>
M-002 やめた <理由>
M-003 問題なし <確かめた結果>
M-004 戻した <戻したコミットの7桁> <理由>
? <返事の文> <なぜ分からないか>
```

最後の行に、全テストの数と clippy の警告数を書く。

## 6. 前提

- 書き換えてよいのは `<作業場所>` と `<結果>` だけ
- プッシュしない
- 計測や確かめのための一時的なコードはコミットしない。終わったら `<作業場所>` の `git status` を空にする
- 人のいない所で動いているので、利用者に質問しない。分からないことは結果に書く
- 報告書・手紙・返事の主張は鵜呑みにせず、コードで確かめる
